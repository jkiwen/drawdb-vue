## Rulings
- **Task 2: Ruling: model imports use explicit `.ts` extensions** — Node v26 `--experimental-strip-types` resolves ESM specifiers literally. Bundlers (Vite/rollup/tsc with `allowImportingTsExtensions`) accept `.ts` extensions. Cost if wrong: slightly non-standard appearance; mitigated by consistent project-wide convention.
- **Task 5: Ruling: SQL import uses `node-sql-parser` + `oracle-sql-parser` instead of a hand-written parser** — The React app already depends on `node-sql-parser`; reusing it keeps the dialects consistent with the export side. Oracle needs the separate `oracle-sql-parser` package because `node-sql-parser` has no `plsql` grammar. Both packages are CommonJS and must be default-imported and destructured. Cost if wrong: two parser dependencies instead of none; accepted because it replaces thousands of lines of hand-written SQL parsing.
- **Task 5: Ruling: `generic` dialect is parsed with the MySQL grammar** — `node-sql-parser` has no portable grammar. The MySQL grammar accepts the common subset, which is what the React app falls back to.
- **Task 6: Ruling: `IndexedDBStorageAdapter` uses the raw IndexedDB API instead of Dexie** — Keeps `@drawdb/core` free of runtime dependencies; the object store layout is three lines of code. Cost if wrong: no query-builder conveniences; not needed for the v1 feature set.
- **Task 6: Ruling: the workspace test runner imports every spec into one process** — `node --test` and vitest both spawn child processes, which the Windows sandbox blocks with `EPERM`. Cost if wrong: no per-file isolation; the specs are pure functions, so isolation is not required.
- **Task 5: Ruling: MSSQL uses a dedicated T-SQL parser instead of `node-sql-parser`** — The `transactsql` grammar of `node-sql-parser` cannot parse foreign keys (`FOREIGN KEY ... REFERENCES ...`, inline `REFERENCES`, `ON DELETE/UPDATE` and `ALTER TABLE ... ADD CONSTRAINT` all throw), so React's `src/utils/importSQL/mssql.js` was dead code. `packages/core/src/sql/import/mssql-parser.ts` parses the T-SQL subset that carries diagram information and emits the same AST shapes the other importers consume. Cost if wrong: ~650 lines of hand-written parsing to maintain; mitigated by 13 dedicated parser specs and by the fact that no other dialect needs it.
- **Task 5: Ruling: referential actions are normalised to the `Constraint` enum** — The React importers store the raw SQL keyword (`"CASCADE"`); the SDK stores `"Cascade"`, `"No action"`, `"Restrict"`, `"Set null"`, `"Set default"` so the export side and the UI share one vocabulary. Cost if wrong: values differ from the React app's stored diagrams; the SDK is a new codebase and does not load React diagrams.
- **Task 5: Ruling: `notNull` is derived from `nullable.type === "not null"`** — React's importer uses `if (d.nullable) field.notNull = true`, which marks an explicitly `NULL` column as `NOT NULL`. The SDK keeps the explicit `NULL` nullable. Cost if wrong: none; the SDK behaviour is the correct one.
- **Task 7: Ruling: `PluginManager` attributes extensions through a per-activation context closure** — A shared `this.currentOwner` field cannot attribute extensions correctly when two plugins activate concurrently. `createContext(base, owner)` binds `registerExtension` in a closure that records the owner, so deactivating a plugin removes exactly the extensions it contributed. Cost if wrong: a context object per activation; negligible.
- **Task 8: Ruling: the DBML layer reuses `@dbml/core` for parsing** — The React app already parses DBML with `@dbml/core`; reusing it keeps the SDK's DBML dialect identical to the app's. The package is CommonJS but exposes a detectable named export, so `import { Parser } from "@dbml/core"` works under Node ESM. Cost if wrong: one runtime dependency in `@drawdb/core`; accepted because a hand-written DBML parser would be far more code and less correct.
- **Task 8: Ruling: the type capability tables are generated from the React `datatypes.js` and shared by the SQL exporters and the DBML exporter** — `scripts/extract-types.mjs` + `scripts/generate-type-registry.mjs` now emit `isSized` / `hasPrecision` / `hasQuotes` / `canIncrement` / `signed` / `hasCheck` / `noDefault` per type for all seven dialects, replacing the hand-written MySQL-only table in `export/dialect-meta.ts`. Cost if wrong: the generated file must be regenerated whenever the React type tables change; mitigated by keeping the generators in `scripts/`.
- **Task 8: Ruling: DBML parse failures raise `DBMLParseError` carrying the `@dbml/core` diagnostics** — The SDK wraps third-party errors so a consumer can show a precise message. Cost if wrong: one extra error type; the original error is not preserved as a cause.
- **Task 9: Ruling: the diagram store holds a `reactive()` diagram, not a `ref()`** — The core commands mutate the diagram in place; a reactive proxy makes those mutations observable to Vue without the store copying the diagram on every edit. Cost if wrong: the store exposes a proxy rather than a plain object, so consumers must not call `structuredClone` on it; mitigated by the core `deepClone()` helper.
- **Task 9: Ruling: `deepClone()` replaces `structuredClone()` in the core commands and the storage layer** — `structuredClone` refuses to clone the proxies a reactive framework hands out; a hand-written recursive clone works on both plain objects and proxies. Cost if wrong: `deepClone` does not handle exotic types (Map/Set/typed arrays) that the diagram model does not use.
- **Task 9: Ruling: the workspace test runner resolves `@drawdb/core` through a Node resolve hook** — The sandbox cannot build the workspace packages and Node refuses to strip TypeScript types under `node_modules`, so the plain workspace symlink is unusable in tests. `scripts/ts-resolver.mjs` remaps the specifier to the core sources. Cost if wrong: test-only machinery; production builds resolve the published package normally.
- **Task 9: Ruling: `vue-demi` and `@vue/devtools-api` are explicit dependencies of `@drawdb/vue-sdk`** — With the hoisted pnpm linker the transitive dependencies of a workspace package are not reachable from it, and `pinia` cannot resolve them. Cost if wrong: two extra declared dependencies; they are required by `pinia` anyway.
- **Task 9: Ruling: pnpm build scripts stay disabled, installs use `--ignore-scripts`** — Running build scripts makes the install fail with `EPERM ... spawn` because the sandbox blocks child processes with piped stdio. The allow-list moved from the `pnpm` field of `package.json` (ignored by pnpm 11) to `pnpm-workspace.yaml`. Cost if wrong: native postinstall steps of dependencies do not run; `vue-demi` is switched to the Vue 3 build with `pnpm rebuild vue-demi`.
- **Task 10: Ruling: the selection and the viewport stay in the UI store, the composables are the API** — Several components have to see the same selection and viewport, and Pinia keeps the state inspectable in the devtools. The composables add the semantics the raw store does not provide, such as resolving the kind of an id from the diagram and converting coordinates. Cost if wrong: the composables cannot be used to hold a second, independent selection.
- **Task 10: Ruling: the composables fall back to a shared pinia instance** — `resolvePinia()` returns the active instance, or a module level fallback when there is none, so the composables work in plain unit tests without duplicating the state implementation. Cost if wrong: state created outside an application is not reset between tests; the tests create their own instance.
- **Task 10: Ruling: the hotkey registry is DOM free and resolves `mod` against the platform** — `createHotkeyRegistry(platform)` matches bindings against plain keyboard event objects, which makes the shortcut behaviour testable without a browser. `mod` means control on Windows and Linux and command on macOS. Cost if wrong: a registry created for the wrong platform ignores the platform modifier.
- **Task 10: Ruling: the drag composable only tracks the movement** — It does not change the diagram; the caller turns the result into a core command, which is what makes a move undoable. Cost if wrong: the caller has to apply the delta itself.
